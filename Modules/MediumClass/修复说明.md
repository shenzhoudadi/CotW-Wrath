# MediumClass 0.3.4 修复说明

本版以 0.3.3 为唯一源码基线，只处理三项反馈：通灵者兼职按总等级发放进度、灵力涌动逐属性独立投骰且日志不显示骰点、阿德里尔恶咒可同时开启三种以上能量。0.3.3 已修复的日志异常隔离、本地化、旧恶咒 GUID 兼容与清理、镜像自身同调活跃判断、一环剩余次数读档、瞬袭与加速叠加均保留，没有回退。

所有验证都是“真实生产源码 + 明确的游戏 API 模型 + 原生程序集/蓝图只读核对”，**没有启动 Unity，没有用户存档，不能替代实机测试**。用户尚未确认这三项已经通过。

## 一、通灵者兼职：按通灵者职业等级授予

### 根因（已用原生程序集核实）
- 原生 `BlueprintProgression.CalcLevel`（Assembly-CSharp，IL 前 12 条指令）：`m_Classes` 与 `m_Archetypes` 都为空时直接返回 **角色总等级**（`UnitProgressionData.CharacterLevel`）。
- 原生 `LevelUpHelper.UpdateProgression` 把已存等级到 `CalcLevel` 之间的条目授予角色，`ApplyClassMechanics.ApplyProgressions` 在**任何职业**升级时都会对角色所有进度重新执行它。
- 0.3.3 的 `MediumProgression.Configure` 没有设置职业（0.3.3 精灵职阶 Archmage 等使用 `AddToClasses`，原生骑将/吟游诗人/血怒者进度的 `m_Classes` 各含自己的职业）。因此骑将 1 + 通灵者 1（总等级 2）只授予“2 级条目”＝降灵会，7 级其他职业 + 通灵者 1 只授予“8 级条目”；之后每升一级其他职业还会继续提前授予 9/10 级条目。
- 用户描述与该机制完全一致。没有测试者存档，此结论来自源码/IL/蓝图，不是复现存档。

### 修改
1. `Medium/MediumProgression.cs`：`.SetClasses(Guids.Medium)`。此后 `CalcLevel` = 通灵者职业等级；单独升级其他职业不能推进通灵者进度；缚灵者的变体额外条目沿用同一进度数据；绝境巡行者是血怒者的变体，走原生血怒者进度，本次没有改动。
2. 新增 `Medium/MediumProgressionMigration.cs`，由 `MediumChannelRestore.Restore`（`UnitDescriptor.ApplyPostLoadFixes` 的既有前缀）**最先**执行，异常一律被吞掉并写 UMM 日志，不会破坏读档。规则（幂等，第二次运行不产生任何修改）：
   - 只看“来源记录为 MediumProgression”的能力层数，对比“通灵者职业等级以内的条目”应得的层数。
   - 缺失的层数补上（只添加能力事实，不写入任何共鸣、每日次数、法术位或已准备法术）。
   - 来源记录为 MediumProgression、但按通灵者职业等级不应存在的层数（例如 Medium 1 时提前得到的降灵会、慰灵之术）被移除，最先移除条目等级最高者。
   - 只考虑“属于该进度自身条目”的能力（任何等级的条目，含变体自己的条目）。原生升级把通过选择项获得的专长（缚灵者额外专长）也记为来源＝该进度，这些专长和选择事实本身**永不触碰**（评审中发现并修正了此处的一个缺陷，见下）。
   - 来源记录为其他进度的层数（例如绝境巡行者的血怒者进度授予的同名能力）一律不当作多余或缺失；补齐的层数不会超过该能力的层数上限，也不会改写已有事实的主来源。
   - 已存进度等级（`ProgressionData.Level`）校正为通灵者职业等级，使下一次升级授予正确的条目。
   - 变体（缚灵者）的选择型条目（额外专长）不能在升级界面之外授予或收回，且选择的专长可能已是别的专长的先决条件：**不处理**，只在日志里报告数量。
   - 多层能力若没有完整的“每层来源”记录（很早期的存档）：不修改，日志报告。

### 旧档能修什么、不能修什么
| 情况 | 处理 |
|---|---|
| 缺失的通灵者 1 级能力（隐藏施法、共鸣、英灵同调等） | 读档时自动补齐 |
| 超前授予的单层能力（降灵会、慰灵之术、三重降灵…） | 读档时自动移除 |
| 超前授予的多层能力（英灵同调、英灵之力、灵力涌动） | 层数超出部分自动移除；层数被别的等级“顶替”的按数量计算，保留 |
| 缚灵者按总等级多得/少得的额外专长选择 | **不自动处理**；建议在游戏或所用工具里对该职业等级重训并重新选择 |
| 没有每层来源记录的多层能力 | 不动，日志报告 |
| 已耗用的共鸣、每日次数、法术位 | 迁移不触碰；补齐的能力只是新增事实，游戏对新增事实怎样初始化资源属于原生行为，**需实机确认** |

若实机发现补齐结果不符合预期，可行的恢复方案是：备份存档后，对该职业等级使用游戏自带或已启用的重训功能，退回并重新选择通灵者等级；重训流程在本次环境中没有验证。

### 验证（`tests/MediumProgressionLevels`，11,985 项）
- 真实 Assembly-CSharp IL：`CalcLevel` 无职业无变体时返回 `CharacterLevel`；`UpdateProgression` 用 `CalcLevel`；`ApplyProgressions` 调用 `UpdateProgression`。
- 真实蓝图（blueprints.zip）：原生 Cavalier/Bard/Bloodrager 进度的 `m_Classes` 只有各自职业。
- 真实生产 `MediumProgression.Configure`（API 替身接住配置调用）+ 逐字转写的原生升级规则：骑将 1→通灵者 1、骑将 7→通灵者 1、其他职业在前 0–19 级再全升通灵者、300 组固定种子随机交错序列，每一步都要求“通灵者等级以内的条目恰好齐全，层数不重复，存储等级等于职业等级”；缚灵者额外专长选择只在通灵者 2/3/5/7/9/11 出现。
- 缚灵者选择的专长（单层、多层）与选择事实在新角色、0.3.3 角色上都不被读档修复删除，层数已满的能力不重复规划（评审回归；对未修正代码这 8 项失败）。
- 旧档：7 类 0.3.3 状态（含骑将 1+通灵者 1）经迁移后条目齐全、幂等，并能继续正常升级；正确存档、无通灵者存档不被修改；其他来源层数、缺少来源记录的层数、缚灵者选择均按上表处理。
- 负对照：0.3.3 的 `MediumProgression.cs` 与 0.3.3 成品 DLL 都被同一程序判定失败；0.3.3 源码在模型里精确复现“骑将 1 + 通灵者 1 只有降灵会、存储等级 8”等现象（`results-neg/progression-0.3.3-source.log`）。

### 仍需实机
新建纯通灵者、骑将 1→通灵者 1、其他职业 7→通灵者 1 的一级完整能力与升级预览；混职升 2/4/6/10/20；缚灵者；绝境巡行者；带 0.3.3 兼职存档的补齐/移除、再保存再读取。见测试指引。

## 二、灵力涌动：一次效果只投一次骰，日志显示骰点与修正明细

### 根因
- 0.3.3 `OnTurnOn` 在属性循环内对每个属性调用 `GetBonus()`（各自 `rnd.Next`），专注查询 `GetStaticConcentrationBonus` 也再调用一次；日志只显示各属性最终数。同一实验（本次同一测试程序）：0.3.3 组件对一次效果抽了 3 个 d6（`results-neg`）。
- 原生 `EntityDataBase.TurnOn` 会在读档/进入区域时重新触发 `Facts.TurnOn`，所以没有持久化的结果每次都会再次随机。

### 修改
- `Medium/SpiritSurgeMath.cs`：`RollDice` 返回 `SurgeRoll`（骰面数与每个骰的结果）；`Roll` 保留为只取总数的包装。规则不变：普通按等级 1d6/1d8/1d10，坚毅灵魂两个独立 d8，绝境巡行者 d6，传奇统帅固定 1d6 且不追加同调。
- `MediumSpiritSurgeComponent` 改用**每实例运行时数据** `SurgeData`（`Version, Sides, Results, Announced`），由游戏随 buff 保存；旧组件 TypeId 不变，新数据类不需要新 TypeId（以程序集限定名解析，与 `MediumTranceOfThreeComponent.TranceData` 相同做法）。
  - 首次使用（`OnTurnOn` 或专注查询）投一次并保存；所有属性、专注、刷新、区域切换、读档都复用；数据损坏（骰面/结果不匹配）时重投一次。
  - 重复 `OnTurnOn`（没有 `OnTurnOff`）先清除本组件修正再应用，不叠加。
  - 新的一次施放会替换旧 buff（原生默认 Replace）＝新的运行时数据＝新投；不同角色的 buff 数据互相独立。共享蓝图与 static 中不保存任何角色骰点。
  - 一次施放只创建一个 buff（`SpiritSurgeBuff` 被三个能力共用，每个能力单目标），专注提供者是同一个组件；没有其他事实使用涌动骰，因此不存在需要另外共享的“同一施放的多个事实”。
  - 旧存档：没有运行时数据（保存的是空组件数据），游戏读档时会丢弃并重建该组件的运行时，游戏日志可能出现一条重建提示；读档后首次使用投一次并保存（仍在持续的旧涌动可能重投一次，最多 5 轮）。
- 统帅附加项仍取自**授予者**（层数＝授予者统帅同调，加授予者有效专攻）；每个属性可有不同附加项，共用的只有骰点。
- 日志与实际加值来自同一个 `SpiritSurgeReport`；每个效果实例只写一行；日志失败不影响能力（`CombatLog` 自身隔离，组件再包一层）。
- 日志格式（本地化键在 `Strings/Medium.json`，模板缺占位符时使用内置措辞）：
  - `B 灵力涌动：1d6 = 4；攻击、意志豁免：骰点 4 + A 的统帅同调 2 + 专攻 1 = +7；专注：骰点 4 + A 的统帅同调 2 + 专攻 1 = +7`
  - 坚毅灵魂：`B 灵力涌动：2d8 = 3 + 6 = 9；攻击：骰点 3 + 6 = 9 + A 的统帅同调 3 = +12`
  - 专攻为 0 时不列出该项；传奇统帅只显示骰点。

### 验证
- `tests/SpiritSurgeScenarios`（472 项）：确定性骰源记录每次抽取；普通涌动等级 1/10/20 × 绝境巡行者 × 多英灵 × 坚毅灵魂各只抽 1 次（坚毅灵魂 2 个 d8）；多属性、重复专注查询、刷新循环不再抽；二次施放重投；两名角色和统帅之令两名盟友互不影响；`Newtonsoft` 按游戏 OptIn 规则真实序列化/反序列化运行时数据，读档后 0 次抽取、数值、日志行数、骰点不变；旧档无数据只投一次；损坏数据重投一次；报告的每个最终加值等于实际修正与专注提供者返回值；接收者自身同调不替换授予者数值；传奇统帅/绝境巡行者/坚毅灵魂骰型；日志抛异常时加值仍在。
- `tests/CombatLog`（16 项）：用实际发布的 `Medium.json` 渲染上述中英文示例的完整字符串，并保留异常隔离、缺模板回退等。
- 负对照：同一程序对 0.3.3 组件在第一条“一次效果只抽一个骰”处失败（抽了 3 次）。

### 仍需实机
真实战斗日志的显示、一次施放两名目标、专注检定、存读档后不变、旧档进行中的涌动。

## 三、阿德里尔恶咒：同时最多两种能量

### 根因
五个变体的执行动作是“已有该 buff 则移除，否则施加”，没有任何计数；伤害组件对每个开启的 buff 各加 1d6。0.3.3 说明文字还写明“可同时开启任意几种”。

### 修改
- 保留五种能量与每种命中挑战目标 +1d6；**负能量与其他四种一样计入两种上限**；允许 0/1/2 种；不自动替换。
- 新增 `ContextActionToggleDeathCurse`（五个变体的实际执行入口）：已有该能量则关闭（任何时候都可关）；否则若已有两种能量开启则**拒绝**并弹出“请先关闭其中一种”的提示；否则开启。判断与改变在同一次调用中基于实时 buff 列表完成，排队的多个命令依次执行也不会超过两种。
- 新增 `AbilityRequirementDeathCurseSlot`：变体按钮的界面限制与提示（不是唯一防线）。
- 伤害组件同样只认前两种（按 buff 列表顺序）：即使第三个开关由旧档、其他模组或别的路径产生，也不会多加伤害。
- 旧档规范化：`MediumChannelRestore.Restore`（读档时）在移除旧成对 buff 之后，把 3–5 个能量开关规范为两个。**策略**：保留 buff 列表中最早的两个（即最先开启的两个，读档保持该顺序），其余移除；不随机；不动其他 buff；幂等；保存后再读不会“复活”第三种。旧成对 buff 兼容 GUID 与清理保持不变。
- 说明文字（中/英）已同步；源码注释、`identifiers-baseline.json` 已更新。新增两个 TypeId（唯一，已对 Assembly-CSharp、TabletopTweaks-Core、ModMenu、BlueprintCore 做冲突审计）：
  - `ContextActionToggleDeathCurse`：`8312c244-24dc-4983-aa1a-68f8677f61c5`
  - `AbilityRequirementDeathCurseSlot`：`19866215-af68-4eaa-9aac-0eb6e6454c4d`
  它们只挂在每次启动重新生成的能力蓝图上，不保存状态；没有修改或删除任何旧 GUID/TypeId。

### 验证（`tests/SpiritInfluenceScenarios`，由 282 项增至 564 项；新增的恶咒专项与成品检查，并改写了原“三个开关各加一份 1d6”的旧断言）
- 五选二的十种组合全部可开；每种组合下其余三种被拒绝（界面限制、执行入口拒绝、有警告、不增伤害）；关闭一种后可换类型；活跃能量始终可关。
- 0/1/2 种；重复点击；五个排队命令依次执行只留两种（前两个）；同一命令重复执行不超限；警告显示失败不影响拒绝。
- 五个开关同时存在时命中只加两份 1d6；旧档 3/4/5 个开关规范为最早两个，其他 buff 与旧成对 buff 不动，幂等，模拟保存再读取不会复活第三种；不同顺序得到确定结果。
- 非自身挑战目标无额外伤害；无阿德里尔降灵无效；降灵结束/休息后清零可重新选择。
- 成品 DLL：五个变体使用新动作和限制、不再直接施加 buff、两个新 TypeId 唯一、恢复入口顺序正确。负对照：0.3.3 成品 DLL 上这 8 项失败（`results-neg/deathcurse-0.3.3-dll.log`）。

### 仍需实机
按钮变灰与提示的显示、执行入口拒绝时的警告文字、存读档、旧档 3–5 种状态的真实恢复、挑战归属。

## 构建与验证环境（诚实说明）

- 云端 Linux，用户目录安装 .NET SDK 8.0.425 与 9.0.318；用 Debian 包（无需 root）提取 Mono 6.12。`dotnet build -c Release`：0 错误，14 条与 0.3.3 相同的既有警告。
- StageMod 的 ILRepack：`MediumClass.csproj` 的 Core 分支使用带反斜杠的 Windows 路径，在 Linux 不能直接执行，**csproj 未修改**。安装 DLL 由固定的 `ilrepack.msbuild.task 2.0.13` 自带的 `ilrepack.exe` 在 Mono 下以与 csproj 相同的参数（`/target:library /out:… MediumClass.dll BlueprintCore.dll`，工作目录为构建输出）合并得到。对照：同法合并 0.3.3 源码，类型/方法集合与随包 0.3.3 成品 DLL 一致（5,806 类型、21,389 方法、17 程序集引用；仅 ILRepack 生成的 GUID 命名内部属性类不同），但字节不同（PE 时间戳/MVID）。**安装包不是在 Windows 上构建的**；需要 Windows 复现时见测试结果文档中的步骤。
- 原生 Harmony 2.0.4：成品元数据签名检查通过（11 个类型、18 个方法引用）；未新增任何 Harmony 补丁。真实安装 Harmony 2.0.4 补丁并执行的两个套件（`InfluenceScenarios`、`SpiritActionBar` 的 net472 模式）在 Linux Mono 上会 SIGSEGV，改用 Lib.Harmony 2.3.6 运行前者、动作条用 net9 + `--reflection-smoke`；这两个套件的 2.0.4 实际安装路径需在 Windows 补跑。
- 严格源码检查（含 C# 语法解析和对游戏/依赖程序集的 TypeId 冲突审计）：0 错误。

## 独立评审记录

交付前对生产代码差异做了一次独立评审（读原生反编译代码核对）。评审发现并已修正一个严重缺陷：通灵者进度恢复最初把“来源记录为 MediumProgression 的所有能力”都当作候选，而原生 `SelectFeature.Apply` 也把通过选择项获得的专长记为该来源，缚灵者额外专长会在每次读档时被删除（新角色也受影响）。已改为只考虑进度自身条目里的能力，并加了回归测试；另修正“层数已满时每次读档重复规划补齐”。评审同时确认：涌动组件对旧存档的重建、读档时机（恢复补丁在 `Facts.PostLoad` 之后、`TurnOn` 之前）、恶咒开关的永久 buff 语义、进度等级校正均与原生代码一致。
